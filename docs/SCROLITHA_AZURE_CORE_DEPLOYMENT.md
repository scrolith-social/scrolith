# Scrolitha Core on Azure Container Apps — Production Runbook

**Status (updated 2026-11-24):** Scrolitha Core is deployed privately in the existing production Container Apps environment. Production AI activation remains off and has not been verified end to end. Historical planning sections below are retained and superseded where this execution record says otherwise.

## Architecture

- Keep the existing `cae-scrolith-sea-prod` environment and API app.
- Deploy the project-owned Ollama Core image as a distinct `ca-scrolitha-core-sea-prod` Container App in that same environment.
- Core uses internal ingress only on port 8080 and has no public route. Same-environment apps reach its generated internal FQDN over HTTPS.
- Use the existing ACR pull user-assigned identity with `AcrPull` scoped to the production registry. Core requires no database, Redis, storage identity, Key Vault secret, public IP, or provider credential.
- Configure the API with the internal HTTPS FQDN, `qwen3:8b`, and sidecar mode off. Preserve current PostgreSQL, Redis, identity, Blob, public API, and health/readiness settings.
- The API Bicep keeps OLLAMA, NATIVE, provider calls, and production-provider gates disabled. Enable persisted/admin settings only after the image scan, cost gate, and real API-to-Core verification pass through the approved activation path.

## Model and capacity

Current source and Core image defaults are `qwen3:8b`; some older docs and certification artifacts state `qwen3:14b`. This runbook resolves the conflict in favor of 8B for the current Consumption-only environment: Microsoft lists a maximum of 4 vCPU/8 GiB per app there, while Ollama’s model library lists 8B at about 5.2 GB and 14B at 9.3 GB. The 14B model is not selected for this profile. The 8B fit remains subject to real inference memory and latency measurements.

Core runs one replica with 4 vCPU/8 GiB, one loaded model, one parallel request, 4096 context, 30-minute keep-alive, and Ollama cloud access disabled. The model is baked into the reviewed image; container startup refuses to download a missing model.

## Recurring cost estimate

The Microsoft Azure Retail Prices API was queried for Southeast Asia on 2026-11-23. Its public USD rates for the Container Apps Consumption profile were `$0.000004` per idle vCPU-second, `$0.000004` per idle GiB-second, `$0.000034` per active vCPU-second, and `$0.000004` per active GiB-second. For 730 hours (2,628,000 seconds) with one 4-vCPU/8-GiB Core replica, that is approximately **$126.14/month while continuously idle** and **$441.50/month if active for all 730 hours**. The first estimate is the compute floor for this always-warm `minReplicas: 1` design; inference processing is billed at the active rate.

These are public list-price estimates for Core only, before free grants, discounts, taxes, logs, image storage, egress, or other resources. Container Apps free grants are shared across the subscription and are not assumed available because the API and other apps may consume them. The internal Core ingress avoids public ingress but does not eliminate log or resource costs. Get an account-specific estimate and configure budget alerts before provisioning. Sources: [Azure Container Apps billing](https://learn.microsoft.com/azure/container-apps/billing), [Azure Container Apps pricing](https://azure.microsoft.com/en-us/pricing/details/container-apps/), and the [Azure Retail Prices API](https://prices.azure.com/api/retail/prices).

The existing Southeast Asia release-guide subtotal is $182.71/month non-HA or $197.31/month for its derived two-node Redis HA estimate, before private endpoints and variable charges. Adding Core's $126.14/month continuously-idle floor gives **$308.85/month non-HA** or **$323.45/month with the derived HA estimate**, before Core image storage, logs, egress, endpoints, and inference-active time. The older $200 ceiling referenced in prior planning is superseded by the owner's current $700/month maximum. No subscription-specific discount or available Container Apps free grant has been verified.

## Deployment sequence (operator runbook; Core deployed, API activation pending)

1. 3. Run and review a fresh `what-if` for `deploy/azure/api-containerapp-single-replica.bicep`, providing the exact API image digest and Core endpoint. Confirm no unrelated live parameters change, especially database, Redis, JWT secret references, Blob, identity, frontend origin, public API origin, and existing API probes.
4. After approval, deploy the API revision with `SCROLITHA_PROVIDER=core`, `SCROLITHA_CORE_ENDPOINT=https://<internal-core-fqdn>`, `SCROLITHA_CORE_MODEL=qwen3:8b`, `SCROLITHA_CORE_SIDECAR_MODE=false`, local-only policy on, OLLAMA and NATIVE environment gates on, production provider-call guard on, and external provider gate off.
5. Keep persisted user-facing feature flags disabled during infrastructure health checks. The admin UI’s saved local loopback endpoint is not proof of the production route; update the persisted admin runtime settings using the supported route after the remote Core is healthy.
6. An administrator with `journeys.templates.manage` updates `/api/admin/scrolitha/config` for admin scope: provider `core`; `coreEndpoint`/`host` equal the Core HTTPS internal FQDN; model `qwen3:8b`; `sidecarMode=false`; `allowGeminiFallback=false`. Verify the saved config and its audit evidence.
7. Enable persisted providers through `/api/admin/ai/providers/NATIVE` and `/api/admin/ai/providers/OLLAMA`; keep all other provider rows disabled. Verify provider reads and health.
8. Through `/api/admin/ai/feature-flags`, enable only `masterEnabled`, `assistantEnabled`, `ASSISTANT_CHAT`, and `enableProviderCalls`. For the latter include `X-Confirm-AI-Risk: CONFIRM`; the deployed environment must also set `SCROLITHA_AI_ALLOW_PROD_PROVIDER=1`. Keep `betaAllowlistOnly` true and do not edit allowlist membership or consent.
9. Validate Core `/api/tags` from within the ACA environment; validate database/Redis `/api/readyz`; check admin health; then send one benign request from an approved synthetic pilot account with recorded consent. Verify provider/model is `OLLAMA`/`qwen3:8b`, no fallback occurred, and audit/usage records are present.

Do not use a local auth bypass, direct database edits, app-setting seed scripts, or environment overrides to manufacture consent or persisted feature state.

## Rollback

1. Disable `enableProviderCalls` through the confirmed admin feature-flag route and verify the durable audit entry.
2. Restore the previous API Container App revision/image and its prior AI environment values using the protected deployment process. Verify `/api/readyz` remains healthy.
3. Keep the Core app internal and disabled/scaled down only after API traffic no longer references it. Do not delete the app or image until logs and rollback evidence are retained.
4. Confirm the prior persisted provider flags/configuration and no requests continue to invoke Core.

### Source-enforced AI usage limits

The local API source currently enforces durable, PostgreSQL-backed reservations and append-only settlements under transaction-scoped advisory locks. Both authenticated and anonymous requests contribute to the global counters; the anonymous identity also receives the per-user controls. Accounting uses UTC calendar-day and calendar-month windows, assigns settlement deltas to the reservation timestamp, and reads persisted ledger rows after process restarts. Quota reservation or settlement persistence failures fail closed. Ollama token usage uses provider-reported prompt and completion counts when available; missing telemetry does not become a fabricated zero.

Source defaults include **100 daily requests per user**, **500,000 monthly tokens per user**, **500,000 global monthly tokens**, **1,000 global monthly requests**, and a 60-second request runtime. The candidate API Bicep overrides both `SCROLITHA_TIMEOUT_MS` and `SCROLITHA_AI_MAX_REQUEST_RUNTIME_MS` to 180 seconds; its frontend request timeout is 210 seconds, below the 240-second Container Apps ingress limit. The global request and token reservations serialize through the global monthly advisory lock. Actual usage that settles beyond a reservation is durably recorded and blocks returning generated output when the configured ceiling is exceeded. Structured/fallback attempts are bounded by the same request deadline and are accounted for in the reservation.

These are application gateway limits, not dollar limits. They do not price Azure compute, replica startup/idle tail time, logs, networking, storage, or requests. Before relying on them for a pilot, confirm every generation route is routed through this quota service and that only the API can reach Core. On a quota/persistence denial, return a blocked response without falling back to Gemini/OpenAI/Mock; alert the operator and disable persisted `enableProviderCalls` using the audited admin route if the operational threshold is reached. Do not use the internal Ollama token-price estimate as an Azure cost calculation.
